# 목표
Sentry MCP로 지난 7일 데이터 조회 → Notion MCP로 [주간 모니터링 보고] DB에 프로젝트별 보고서 페이지 생성.

# 절대 규칙
- 숫자는 Sentry/Notion 조회값만 사용. 추측 금지.
- 값을 못 구하면 `-` 기입 + 최종 요약에 사유 기재.
- 아래 "수정 허용 영역" 외 본문은 템플릿 원본 그대로 유지.
- 체크박스 체크 금지.
- 기존 페이지 수정·삭제 금지. 새 페이지 생성, 이슈 행 추가, 새 페이지의 이슈 상세 뷰 필터 설정만 허용.

# 변수
| 이름 | 값 |
| --- | --- |
| DB_URL | {실제 [주간 모니터링 보고] DB URL} https://app.notion.com/p/41e9f9111862803d8903c5e1ebe6e045?v=3559f911186283bda303886a75a0dd01&source=copy_link |
| RUN_DATE | 실행일 (YYYY-MM-DD) |
| START_DATE | RUN_DATE - 6일 |
| PERIOD | START_DATE ~ RUN_DATE (7일, 양 끝 포함) |
| MONTH_TAG | RUN_DATE 기준 `YYYY.MM` |

예: RUN_DATE=2026-11-09 → PERIOD=2026-11-03 ~ 2026-11-09, MONTH_TAG=2026.11

# 매핑
Sentry 프로젝트 slug 형식: `{접두어}-{서비스키}` (예: pj-antiscam, partner-couponwallet)

| 접두어 | 템플릿 |
| --- | --- |
| partner | 기본 템플릿 (partner) |
| pj | 기본 템플릿 (pj) |
| hp | 기본 템플릿 (홈페이지) |
| svc | 기본 템플릿 (svc) |

## 서비스키 → 서비스명
| 서비스키 | 서비스명 |
| --- | --- |
| mfinder | 휴대폰분실보호 |
| couponwallet | 휴대폰쿠폰지갑 |
| antiscam | 스마트피싱보호 |

- 매핑 없는 프로젝트: 생성 안 함. 요약에 "건너뜀(매핑 없음)" 기재.

# 작업 순서

## 1. 대상 프로젝트 선정
- Sentry 조직 프로젝트 목록 조회.
- 매핑 표에 있는 접두어 + 서비스키 조합만 선정.
- 생성(작성) 순서: 서비스명 순(휴대폰쿠폰지갑 > 휴대폰가족보호 > 휴대폰분실보호 > 스마트피싱보호 > 오토콜) → 같은 서비스명 안에서는 접두어 순(partner > pj > hp). 위 순서대로 페이지를 생성하고, 요약 표도 같은 순서로 출력.

## 2. 중복 확인
- DB_URL에서 `프로젝트명` = slug AND `모니터링 일자` = RUN_DATE 페이지 검색.
- 있으면 해당 프로젝트 전체 건너뜀. 요약에 "이미 존재" 기재.

## 3. Sentry 금주 데이터 조회 (production environment만)
- 모든 조회에 `environment:production` 조건을 반드시 포함. 다른 environment(development 등)는 제외.

| 항목 | 정의 |
| --- | --- |
| 금주 Error | 해당 프로젝트 에러 이벤트 총 수 (count()). 기간은 PERIOD(달력)가 아니라 **조회 시점 기준 최근 7일 상대 기간(`statsPeriod=7d`)**. Sentry 대시보드의 7D와 같은 숫자여야 함 |
| 금주 신규 Issue | 금주 Error와 동일하게 PERIOD(달력)가 아니라 **조회 시점 기준 최근 7일 상대 기간(`statsPeriod=7d`)**. `environment:production` 기준으로 이 기간 안에 처음 발생한 이슈 수 (Sentry 상태 `New`). 이슈 단위 firstSeen 필터는 다른 환경에서 먼저 생긴 이슈를 놓치므로 쓰지 않고, `environment:production` 조회 결과의 firstSeen이 7일 안인 이슈를 집계 |
| 신규 이슈 목록 | 위 이슈별 title, firstSeen 날짜(YYYY-MM-DD) |

## 4. 전주 값 조회 (Notion)
- DB_URL에서 `프로젝트명` = slug AND `모니터링 일자` < RUN_DATE 중 가장 최근 페이지 1개 선택.
- 그 페이지 "전체 현황" 표의 **금주** 열 값을 이번 **전주** 값으로 사용.
  - Error 행 금주 → 이번 Error 전주
  - 신규 Issue 행 금주 → 이번 신규 Issue 전주
- 이전 페이지 없음 / 값이 `-` / 숫자 아님 → 전주 `-`.

## 5. 증감 계산
- 증감 = 금주 - 전주
- 표기: 양수 `+N`, 음수 `-N`, 같으면 `0`
- 금주 또는 전주가 `-` → 증감 `-`

## 6. 페이지 생성
- DB_URL에 접두어 매핑 템플릿으로 새 페이지 생성.
- 템플릿 적용 불가 시: 생성 중단, 사유 보고. 본문 직접 작성 금지 (인라인 DB가 템플릿에만 있음).

### 속성
| 속성 | 값 |
| --- | --- |
| 프로젝트명 | slug |
| 모니터링 일자 | RUN_DATE |
| 서비스명 | 서비스키 매핑값 |
| 신규이슈 | 금주 신규 Issue 수 (텍스트, 예: "2") |
| 선택 | MONTH_TAG (옵션 없으면 추가) |
| 상태 | 진행중 |
| 조치현황 | 비움 |
| 담당자 | 비움 |

### 수정 허용 영역 1: 모니터링 개요 표
| 항목 | 내용 |
| --- | --- |
| 모니터링 일자 | {RUN_DATE} |
| 모니터링 기간 | {START_DATE} ~ {RUN_DATE} (7D) |
| 대상 프로젝트 | {slug} |
| 담당자 | 담당자 |

### 수정 허용 영역 2: 전체 현황 표
| 구분 | 설명 | 전주 | 금주 | 증감 | 비고 |
| --- | --- | --- | --- | --- | --- |
| Error(에러 수) | 발생 에러 수 | {전주} | {금주} | {증감} |  |
| 신규 Issue | 발생한 신규 이슈 | {전주} | {금주} | {증감} |  |
| 미해결 Issue | `unresolved` 이슈 | - | - | - |  |

- 미해결 Issue: 작성자 판단 영역. 전부 `-`.
- 비고: 비움.

### 수정 금지 영역
- 종합 결과 체크리스트 (항목만 유지, 체크 금지)
- 금주 주요 오류 이슈 상세의 안내문, 인용 블록, 상태 정의 표
- 배포 영향 확인 전체
- 최종 결과 (종합 판단), 특이사항

## 7. 신규 이슈 행 추가
- 새 페이지의 "금주 주요 오류 이슈 상세" 인라인 DB 확인.
- 링크된 뷰면 원본 DB를 찾아 원본에 추가.
- 추가 전 속성 조회. `이슈`, `작성일`, `서비스명` 3개 존재 확인.
  - 하나라도 없으면 추가 안 함. 요약에 실제 속성 목록 기재.
  - `구분` 속성이 있으면 반드시 `신규` 옵션으로 입력. 비워두지 않음. `신규` 옵션이 없으면 추가하지 말고 요약에 기재. `구분` 속성 자체가 없는 DB만 `구분` 입력을 생략하고 요약에 기재.
- 이슈명 정리:
  - Sentry title 맨 앞의 `Error: ` 접두사를 반드시 제거한 값을 이슈명으로 사용. 이슈 행에 `Error: ` 접두사가 남아 있으면 안 됨. 예: `Error: Na` → `Na`, `Error: [GiftShare] 공유 버튼 생성 실패` → `[GiftShare] 공유 버튼 생성 실패`.
  - `TypeError:`, `ReferenceError:`, `ApiError:` 등 다른 에러 타입은 제거하지 않고 그대로 유지.
  - 접두사 제거 후 이슈명이 같은 이슈가 여러 개면 1행만 작성. 스택트레이스가 달라 같은 이슈가 다르게 집계된 것으로 간주.
  - 중복 제거는 이슈 행에만 적용. 6단계의 `신규이슈` 속성과 전체 현황 표의 신규 Issue 수는 Sentry 원본 수 그대로 기입.
- 이슈명 1개당 1행:
  | 속성 | 값 |
  | --- | --- |
  | 이슈 | `Error: ` 접두사 제거한 이슈명 |
  | 작성일 | {RUN_DATE} (이슈 발생일 firstSeen이 아니라 보고서 작성일) |
  | 서비스명 | 서비스키 매핑값 |
  | 구분 | 신규 |
- 같은 이슈명 + 같은 작성일({RUN_DATE}) 행이 이미 있으면 추가 안 함.
  - 비교는 접두사 제거한 이슈명과 정확히 일치하는 행만 대상. 기존 행에 `Error: ` 접두사가 붙어 있으면 다른 행으로 보고 건너뛰지 않고 추가.

## 8. 이슈 상세 뷰 필터 설정
- 7단계의 인라인 DB 뷰에 `작성일` 필터(모니터링 기간과 동일)와 `서비스명` 필터(해당 문서의 서비스명)를 함께 설정. 신규 이슈가 0건이어도 설정.
- 뷰의 기존 필터(템플릿에 남은 이전 기간 필터 포함)는 제거하고 아래로 교체:
  - `notion-update-view` configure: `CLEAR FILTER; FILTER "작성일" >= "{START_DATE}" AND "작성일" <= "{RUN_DATE}" AND "서비스명" = "{서비스명}"`
  - `{서비스명}`은 6단계 속성의 `서비스명` 값(서비스키 매핑값)과 동일.
- 뷰 자체에 저장되는 필터로 설정해 모든 사용자에게 적용. 개인 필터·빠른 필터로 두지 않음.
- 설정 후 뷰를 다시 조회해 필터가 반영됐는지 확인. 실패하면 요약에 사유 기재.

# 최종 요약 (출력 형식)
| 프로젝트 | 서비스명 | 이슈 행 추가 수 | 결과 | 페이지 링크 |
| --- | --- | --- | --- | --- |

- 결과 값: 생성 / 이미 존재 / 건너뜀(매핑 없음) / 실패
- 위 표만 출력. 프로젝트별 상세 블록, Error·신규 전주/금주/증감, 추가한 이슈 행 내용은 출력하지 않음.
- 표 아래에는 `-` 기입, 실패, 이슈 상세 뷰 필터 설정 실패가 있을 때만 프로젝트명과 사유를 한 줄씩 기재. 없으면 아무것도 쓰지 않음.

# Slack 알림
- 레지스트리의 `주간 리포트 Slack 채널` 값이 있으면, 모든 프로젝트 처리가 끝난 뒤 한 번만 보낸다. 값이 없으면 건너뛴다.
- 채널 ID는 레지스트리 값을 그대로 쓴다. 채널을 새로 찾지 않는다.
- 메시지 형식:
  - 제목: `*Sentry 주간 모니터링 보고서 작성 완료 · {RUN_DATE}*`
  - 기간 줄: `기간 \`{START_DATE} ~ {RUN_DATE}\` · 대상 N개 프로젝트`
  - 최종 요약 표: 프로젝트 | 서비스명 | Error | 신규 Issue | 결과
  - 결과 셀의 페이지 링크는 `<페이지 URL|열기>`, 링크 텍스트의 `|`는 쓰지 않는다.
  - 건너뜀·실패 행은 Error와 신규 Issue를 `-`로 쓰고 결과 셀에 사유를 쓴다.
- Slack 전송 실패는 건너뛰고 요약에 사유를 적는다. 이미 만든 Notion 페이지는 되돌리지 않는다.
- 위 "최종 요약 (출력 형식)"의 채팅 출력 규칙은 그대로 둔다. Slack 메시지는 이 단계에서만 보낸다.
