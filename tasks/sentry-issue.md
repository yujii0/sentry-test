# Sentry 이슈 정리 (/sentry-issue)

Sentry Alert가 GitHub에 자동 생성한 이슈를 Sentry 데이터와 매핑된 코드 레포의 코드로 분석해서, 아래 템플릿 형식으로 본문 초안을 작성한다.
Claude는 초안까지만 작성하고, 승인은 관리자가 한다.

## 0. 사전 확인 — 레지스트리 읽기

**레지스트리 파일: `tasks/sentry-projects.md` (이 레포 루트 기준)**

- 가장 먼저 Read 도구로 위 파일을 읽는다.
- 이 명령에서는 레지스트리가 유일한 기준이다. 현재 폴더나 프로젝트 폴더 `CLAUDE.md`의 `## Sentry` 섹션 유무는 확인하지 않는다.
- 레지스트리에서 다음을 읽는다.
  - Sentry 조직
  - GitHub 이슈 레포 (이하 `<이슈 레포>`)
  - 매핑표: Sentry 프로젝트 slug → 코드 레포 (`owner/repo`)
- 파일이 없거나 위 항목 중 하나라도 없으면 아무것도 수정하지 말고, 무엇이 없는지 알려준 뒤 끝낸다.
- 사용자에게 폴더를 지정하거나 다른 폴더에서 다시 실행하라고 요청하지 않는다.

## 1. 대상 이슈 찾기

- 인자가 있으면 그 이슈 하나만 처리한다: `gh issue view <이슈번호> --repo <이슈 레포> --json number,title,body,url,labels`
  - `Triage: new` 라벨이 없는 이슈면 수정하지 말고 이유를 알려준 뒤 끝낸다.
- 인자가 없으면 `Triage: new` 이슈 전체를 처리한다:
  `gh issue list --repo <이슈 레포> --label "Triage: new" --state open --limit 20 --json number,title,body,url`
- 대상이 없으면 "처리할 이슈 없음"이라고 알리고 끝낸다.

## 2. Sentry 상세 조회

- 이슈 본문에서 Sentry 이슈 링크나 short ID를 찾는다.
- 레지스트리의 Sentry 조직에서 Sentry MCP로 다음을 조회한다:
  **Sentry 프로젝트 slug**, 에러 메시지와 타입, 전체 스택트레이스, 최초 발생 시각, 환경, 릴리스, 주요 태그(브라우저, OS, 기기, URL), 브레드크럼.
- Sentry 링크를 찾지 못했거나 조회에 실패하면 그 이슈는 건너뛰고, 마지막 보고에 사유를 적는다.

## 3. 코드 분석

### 3-1. 코드 위치 찾기

- 조회한 Sentry 프로젝트 slug로 레지스트리 매핑표에서 코드 레포를 찾는다.
- **매핑표의 코드 레포만 사용한다.** 다른 레포를 검색해서 코드 위치를 추측하지 않는다.
- 아래 경우에는 코드 분석 없이 Sentry 데이터만으로 초안을 쓰고, 원인 분석 요약 끝에 `(코드 미확인)`을 붙이고, 마지막 보고에 사유를 적는다.
  - 매핑표에 slug가 없음
  - 코드 레포가 `-` 또는 `?`
  - 코드 레포에 접근할 수 없거나 파일을 찾지 못함

### 3-2. 분석

- 검색과 읽기는 그 코드 레포 안에서만, 읽기 전용으로 한다. `node_modules`, `dist`, `build`, `.next` 같은 빌드/의존성 폴더는 제외한다.
- 해당 코드 레포의 `CLAUDE.md`가 있으면 프로젝트 규칙으로 참고한다.
- 스택트레이스에서 이 프로젝트 코드에 해당하는 프레임(라이브러리 내부 제외)을 찾아 해당 파일과 함수를 읽는다.
  배포된 경로(예: `src/...`, `webpack://...`)를 코드 레포의 파일 경로로 맞춰 찾는다.
- 브레드크럼과 태그를 함께 보고, 어떤 상황에서 에러가 나는지 재현 조건을 추정한다.
- 확실하지 않은 내용은 `(추정)`, 확인할 수 없는 항목은 `(확인 필요)`로 표시한다. 없는 내용을 지어내지 않는다.

## 4. 본문 작성

### 4-1. 구조

세 섹션 제목(이모지 포함)과 순서, 그 아래 소제목은 아래와 똑같이 쓴다.
조치 계획의 소제목은 해당 내용이 없으면 생략한다.

```
### 📌 이슈 정보
### 🔍 발생 원인
  #### 핵심 스택트레이스
  #### 원인 분석
  #### 재현 조건
### 🛠 조치 계획
  #### 즉시 수정      (일반 이슈)
  #### 재발 방지      (일반 이슈)
  #### 노이즈 판단    (노이즈 의심 이슈 — 4-4 참고)
  #### 확인 필요
```

### 4-2. 분량 규칙 (간결하게)

**간결하고, 명확하고, 단답형으로 쓴다.** 읽는 사람이 30초 안에 파악할 수 있어야 한다.

- 서술형 문장 대신 **단답형/명사형**으로 끝낸다. (예: "Body 없는 응답 미검증", "팝업 오픈 전 ErrCode 확인 추가")
- 한 항목은 **한 줄**. 설명이 길어지면 핵심만 남기고 자른다.
- 개수 상한:
  - 원인 분석 근거: 최대 3개
  - 재현 조건: 최대 3단계
  - 조치 계획: 소제목마다 최대 3개
  - 문제 코드 블록: 최대 2개, 각 5줄 이내
  - 스택트레이스 프레임: 이 레포 코드 3~5줄
- 같은 내용을 여러 섹션에서 반복하지 않는다.
- 접속사, 수식어, "~입니다/~합니다" 같은 어미를 쓰지 않는다.

### 4-3. 마크다운 규칙 (가독성)

GitHub 이슈에서 한눈에 읽히도록 다음을 지킨다.

- **Sentry 링크는 📌 이슈 정보의 맨 첫 줄**에 둔다: `**Sentry** · [SHORT-ID](링크)`
- 이슈 정보는 **2열 표**(항목 | 내용)로 쓴다. 표 안의 `|` 문자는 `\|`로 바꾼다.
- 파일 경로, 함수명, 변수명, 에러 메시지, 릴리스, 환경 값은 모두 `인라인 코드`로 감싼다.
- 문제 코드는 **파일 확장자에 맞는 언어 태그**로 코드 블록을 쓴다 (`.tsx` → `tsx`, `.ts` → `ts`, `.js`/`.jsx` → `jsx`, `.kt` → `kotlin`, `.py` → `python` 등).
  - 코드 블록 바로 위에 `**파일경로:라인** · 함수명`을 한 줄로 쓴다.
  - 에러가 난 줄 앞뒤 1~2줄만 넣고, 에러 줄 끝에 언어에 맞는 주석으로 `← 에러 발생`을 단다.
- 스택트레이스 프레임 목록은 ` ```text ` 코드 블록으로, 이 레포 프레임만 3~5줄 넣는다.
- 원인 분석은 맨 위에 GitHub 알림 블록으로 **한 줄 요약**을 두고, 근거는 번호 목록으로 쓴다.
- 재현 조건은 사용자가 겪는 순서대로 번호 목록으로 쓴다.
- 섹션 사이와 소제목 아래에는 빈 줄을 넣는다.
- `(추정)`, `(확인 필요)` 표시는 항목 끝에 붙인다.
- 발생 횟수, 영향받은 사용자 수처럼 계속 바뀌는 수치는 쓰지 않는다. 최신 수치는 Sentry 링크에서 확인한다.

### 4-4. 노이즈 의심 이슈

아래처럼 코드 수정이 필요 없어 보이는 경우 노이즈 의심으로 판단한다.

- 브라우저 확장 프로그램, 외부 스크립트(광고, 분석 도구 등)에서 난 에러
- 봇, 크롤러, 매우 오래된 브라우저에서만 난 에러
- 사용자의 네트워크 끊김, 요청 취소(`AbortError`, `Network Error` 등)
- `ResizeObserver loop` 같은 무해한 브라우저 경고성 에러
- 테스트/개발 환경에서만 난 에러

노이즈 의심이면:
- 📌 이슈 정보, 🔍 발생 원인은 평소처럼 짧게 쓴다. 원인 분석 요약에 노이즈로 보는 이유를 쓴다.
- 🛠 조치 계획은 `즉시 수정`, `재발 방지` 대신 `#### 노이즈 판단`만 쓴다 (4-5 예시 B).
- 판단만 적고 라벨은 붙이지 않는다. Discard/Archived 처리는 담당자가 협의 후 한다.

### 4-5. 출력 형식 예시

아래 형식을 그대로 따른다. `<>` 부분만 실제 내용으로 바꾸고, 해당 내용이 없는 표 행이나 목록 항목은 뺀다.

**예시 A. 일반 이슈**

````markdown
### 📌 이슈 정보

**Sentry** · [<SHORT-ID>](<Sentry 이슈 링크>)

| 항목 | 내용 |
| --- | --- |
| 에러 | `<에러 타입>: <메시지>` |
| 발생 위치 | `<파일 경로>:<라인>` · `<함수/컴포넌트명>` |
| 호출 위치 | `<파일 경로>:<라인>` · `<함수/컴포넌트명>` |
| 환경 | `<environment>` |
| 릴리스 | `<release>` |
| 최초 발생 | <YYYY-MM-DD HH:mm> (KST) |
| 주요 환경 | <브라우저> · <OS> · <기기> |
| 발생 URL | `<URL>` |

### 🔍 발생 원인

#### 핵심 스택트레이스

```text
<에러 타입>: <메시지>
  at <함수명> (<파일 경로>:<라인>:<컬럼>)
  at <함수명> (<파일 경로>:<라인>)
```

**`<파일 경로>:<라인>`** · `<함수/컴포넌트명>`

```tsx
<에러 줄 앞 코드>
<에러가 난 코드> {/* ← 에러 발생 */}
<에러 줄 뒤 코드>
```

#### 원인 분석

> [!IMPORTANT]
> <원인 한 줄 요약 (예: 캡차 응답의 Body 누락 미검증)>

1. <근거 1 (예: `onSuccess`에서 `Header.ErrCode` 미확인)>
2. <근거 2 (예: `CaptchaPopup`에 방어 코드 없음)> (추정)

#### 재현 조건

1. <행동 1 (예: 해지 화면 진입)>
2. <행동 2 (예: "인증번호 받기" 클릭)>
3. <조건 (예: Body 없는 응답 수신)>

> [!NOTE]
> <참고 한 줄 (예: `Refund`, `join` 페이지에 동일 패턴)> (추정)

### 🛠 조치 계획

#### 즉시 수정

- [ ] `<파일 경로>` · `<함수명>` — <할 일 (예: ErrCode 실패 시 팝업 미오픈)>
- [ ] `<파일 경로>` · `<함수명>` — <할 일 (예: `Body?.ImgB64` 없으면 렌더 생략)>

#### 재발 방지

- [ ] <할 일 (예: 캡차 실패 응답 로깅)>

#### 확인 필요

- [ ] <확인할 것 (예: 동일 패턴 페이지 수정 범위)>
````

**예시 B. 노이즈 의심 이슈** — 📌 이슈 정보는 예시 A와 같고, 발생 원인은 짧게, 조치 계획은 노이즈 판단만 쓴다.

````markdown
### 🔍 발생 원인

#### 핵심 스택트레이스

```text
<에러 타입>: <메시지>
  at <외부 스크립트 또는 확장 프로그램 프레임>
```

#### 원인 분석

> [!IMPORTANT]
> 노이즈 의심 — <이유 한 줄 (예: 브라우저 확장 프로그램 스크립트에서 발생, 서비스 코드 프레임 없음)>

#### 재현 조건

1. <조건 한 줄 (예: 특정 확장 프로그램 설치된 Chrome)> (추정)

### 🛠 조치 계획

#### 노이즈 판단

- 판단 근거: <어떤 경우의 노이즈인지 한 줄>
- [ ] 협의 후 Discard 또는 Archived 처리

````

### 4-6. 공통 원칙

- 사용자 이메일, IP, 사용자 ID, 토큰, 비밀번호, API 키 같은 개인정보와 비밀값은 쓰지 않는다.
  스택트레이스, 코드, 브레드크럼에 비밀값이 보이면 `[마스킹됨]`으로 바꾸고, 마지막 보고에 알린다.
- 위 구조 밖에 다른 섹션이나 인사말, 맺음말을 추가하지 않는다.

## 5. 이슈 수정

- 본문을 레포 밖 시스템 임시 폴더의 `sentry-issue-<이슈번호>.md`에 저장한다. 레포 안에는 파일을 만들지 않는다.
- 이슈 본문과 라벨을 수정한다:
  `gh issue edit <이슈번호> --repo <이슈 레포> --body-file <임시파일> --add-label "Triage: ai-drafted" --remove-label "Triage: new"`
- 제목은 바꾸지 않는다.

## 6. 금지 사항

- **쓰기 가능한 레포는 이슈 레포(`<이슈 레포>`) 하나뿐이다.** 매핑표의 코드 레포(예: `pj.antiscam.co.kr`)는 Sentry 이슈 분석을 위해 코드를 읽는 용도로만 쓴다. 파일 수정, 브랜치 생성, 커밋, push, PR·이슈·코멘트 생성 등 어떤 쓰기 작업도 절대 하지 않는다. 클론하더라도 읽기만 한다.
- 이슈 조회·수정 gh 명령에는 반드시 `--repo <이슈 레포>`를 붙인다. 코드 레포는 읽기 외의 gh 명령을 실행하지 않는다.
- `Triage: approved` 라벨, 노이즈/모니터링 같은 분류 라벨은 붙이지 않는다. 관리자가 한다.
- 이슈를 닫거나, 새 이슈를 만들거나, 코멘트를 달지 않는다.
- Sentry 이슈의 상태(resolve, assign 등)를 바꾸지 않는다.

## 7. 결과 보고

마지막에 아래 형식으로 보고한다.

| 이슈 | Sentry 프로젝트 | 결과 | 한 줄 요약 |
| --- | --- | --- | --- |
| #번호 | slug | 초안 작성 / 초안 작성(노이즈 의심) / 초안 작성(코드 미확인) / 건너뜀(사유) | 에러 원인 한 줄 |

마스킹한 비밀값이 있었다면 이슈 번호와 함께 따로 알린다.

## 8. Slack 알림

- 레지스트리의 `Slack 알림 채널` 값이 있으면, 처리한 이슈를 한 메시지로 묶어 보낸다. 없으면 건너뛴다.
- 채널 ID는 레지스트리 값을 그대로 쓴다. 채널을 새로 찾지 않는다.
- 메시지 형식:

```
**[Sentry 이슈 초안 작성 완료]**

[#번호](이슈 URL) [`Sentry ID`](Sentry 이슈 URL) · `slug`
• 원인: <한 줄>
• 라벨: `Triage: ai-drafted`
```

- 이모지는 쓰지 않는다. 강조는 bold, 코드 값은 인라인 코드로만 쓴다.
- 본문 상세와 조치 계획은 GitHub 이슈에만 쓴다. Slack에는 요약만 보낸다.
- Slack 전송 실패는 건너뛰고 마지막 보고에 사유를 적는다. GitHub 이슈 수정은 되돌리지 않는다.
